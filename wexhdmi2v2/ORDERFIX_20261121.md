## Exact code-level collision — independently reproducible

The 0.8.3-pinned source \`XE::processDisplay13Framebuffer()\` installs:
1. \`display13FBOutputHooksReady=processDisplay13FramebufferOutput(...)\`;
2. only afterwards \`display13FBTCHooksReady=processDisplay13FramebufferTC(...)\`.

The V2 \`wexhdmi2v2/prepare.py\` inserted its early CALL site rewrite inside **processOutput**:
\`\`\`cpp
patcher.routeBlock(address + 0x4FFB6, patchedCall, 5);
\`\`\`

But the downstream native TC validation \`processDisplay13FramebufferTC()\` performs exact \`memcmp\` against all \`Display13TC::Native::spans\`, including this original **seven-byte** sequence in \`kern_display13_tc_native.hpp\`:
\`\`\`cpp
innerCallOffset = 0x4FFB6;
innerCall[] = {0xE8,0x67,0x0B,0x00,0x00,0xEB,0x1C};
\`\`\`

By design, V2 overwrites the first five bytes with \`E8 rel32\`; the subsequent \`memcmp\` must fail unless the replacement happens to be the original no-op relative target (which it is not). \`processTC()\` returns false, \`WEXDisplay13TCHooksReady=No\`, the Display13 contract reports missing capabilities, and the startup falls back to the boot framebuffer. This precisely explains the regression without assuming a Metal/PHY/SCDC hardware failure.

## Patch contained on this separate branch (NOT the failed original V2)

- Install-order correction: move the optional V2 CALL patch **after** \`display13FBTCHooksReady=processDisplay13FramebufferTC(...)\`. Gate patch on OutputHooksReady and TCHooksReady. This removes the specific signature collision but **does not prove** the added wrapper is safe at runtime.
- \`-wex-yoga-hdmi2-callsite-observe\` is now **genuinely passive**: checks original bytes and prerequisites, reports status **6**, never executes \`routeBlock\`, never sends extra SCDC commands, never writes the HDMI2 source bits. \`WEXYogaHDMI2PassiveReady=Yes\` indicates software preflight only; no actual LightUpTMDS hook is present.
- \`-wex-yoga-hdmi2-callsite-safe\` still opts in to the CALL patch, now after the native TC checks, but it remains **RESEARCH ONLY**, blocked for actual machine testing. Other risks are not yet resolved: changed native return PC, DDC owner state, 0xA8 not responding, 4K60 -> 4K30 rollback and USB-C dock failure.
- No change to SST, Deep8, HDMI600, eDP120 stable operation or user's daily EFI.
- New \`wexhdmi2v2/test_plan.py\` guards exact original seven-byte signature, its validation order, conditional patching after TC and passive observe branch.

## Hard limits

Fixing the order collision removes **one directly proven cause** of failed framebuffer startup. It is not sufficient to claim real 4K60 output works. There is no real test of \`LightUpTMDS\` wrapper, native SCDC access, or failure rollback. The CI is compile and mocked static tests only.

User should not use the earlier V2 binary or its old observe flag under any circumstances. If returning to daily usage, restore the already-validated stable WhateverXe and drop all V2 and V1 HDMI2 options. The orderfix branch is provided to retain the investigation and prevent repeating the root cause; a later safe implementation should prefer existing routed Display13 mode/DDC hooks rather than modifying a TC-validated CALL.
