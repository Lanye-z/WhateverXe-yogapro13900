# E1.2-HDMI600-RGB8 — external display colour experiment

**Source / tooling stage only. This is not a validated hardware fix.**

Parent: E1.1-HDMI600 commit 91629bd10c5d40f41a6df76e8daf96a87ab0ed07.
The original E1.1 branch, pinned E1.0 Display13 multi-output source,
HDMI600 runtime patch, WhateverXe Graphics 0.4.0 and EFI are unchanged.
This branch adds no compiled Kext changes and no new boot arguments.

## Background

WhateverXe issue #40 reported purple HDMI output restored by limiting
YCbCr, deep-colour and HDR capabilities in a monitor-specific macOS EDID
override. Issue #41 separately fixed the 300MHz mode admission ceiling;
the author preserved 4K60 timings and 600MHz HDMI capabilities in the EDID.

Links:
- https://github.com/b00t0x/WhateverXe/issues/40
- https://github.com/b00t0x/WhateverXe/issues/41

Those reports involve a desktop UHD 770. They do not confirm a solution on
Yoga A7A0, Display13 or a USB-C DP-to-HDMI conversion dock.

## Step 1: identify the real external EDID

With the external display connected, export EDID candidates:

~~~sh
ioreg -p IOService -l -w0 | grep IODisplayEDID > ~/Desktop/edid-list.txt
~~~

An ioreg dump may include both the internal eDP and external display.
Do not assume the first entry is HDMI. Prefer a verified EDID binary
for the actual monitor. Display IDs are printed by the inspect command:

~~~sh
python3 e12/tools/edid_rgb8.py ~/Desktop/external-edid.bin --inspect-only
~~~

The script accepts a single 128-byte-multiple binary EDID, a plain hex
EDID, or an ioreg text file. If more than one EDID is found, it **refuses**
to select one without an explicit --index N. Verify VID/PID/model against
the actual external monitor before generating or installing anything.

## Step 2: generate both versions offline

~~~sh
python3 e12/tools/edid_rgb8.py ~/Desktop/external-edid.bin \
    --out ~/Desktop/E1.2_RGB8_Output
~~~

Results:
- ORIGINAL_EDID_BACKUP.bin — untouched source EDID
- RGB_ONLY.bin — CTA YCbCr444/422 flags and YCbCr420 data blocks removed.
  Base input bit depth, HDMI deep-colour and HDR blocks are unchanged.
  This is a colour-format diagnostic, **not guaranteed RGB 8-bit**.
- RGB8_STRICT.bin — further declares 8 bpc in base EDID; clears HDMI
  VSDB deep-colour and HDMI Forum 420 deep-colour support, and removes
  CTA static/dynamic HDR blocks.
- REPORT.json — IDs, checksums, exact transformations
- RGB_ONLY/DisplayVendorID-xxxx/DisplayProductID-yyyy — plist override
- RGB8_STRICT/DisplayVendorID-xxxx/DisplayProductID-yyyy — plist override

The generator checks every EDID checksum and extension count, retains
normal CTA video blocks and DTD timings and keeps the HDMI 600MHz TMDS
capability byte and SCDC flags unchanged. It refuses a monitor that
advertises 4K60 only as a YCbCr420 video data block, since deleting
that block would lose the corresponding 4K60 mode.

It does not claim that every EDID encodes 4K60 identically. For sources
without a recognized RGB-capable 4K60 mode, the tool cannot promise 4K60.
Unknown/proprietary vendor blocks are preserved, including vendor-specific
HDR metadata that may still influence the display.

## Step 3: test cautiously — manual only

Do not replace E1.1 WhateverXe.kext or your working EFI. Keep a recovery
EFI intact. The script **never** installs overrides, edits /Library,
modifies an EFI, runs sudo or changes any active display state.

Before installing, back up any existing file at the exact display override
path. A previous override may be important for getting a working image.
For one selected variant, the expected macOS override layout is:

~~~text
/Library/Displays/Contents/Resources/Overrides/
  DisplayVendorID-xxxx/
    DisplayProductID-yyyy
~~~

The generated plist has the matching display VID/PID and binary EDID.
Copying this plist into /Library is a *separate administrator action*.
macOS Tahoe may handle override reloads differently, so verify that the
new EDID is in use after a controlled reboot.

Test only one variant at a time:
1. Confirm the external output path: native HDMI vs USB-C DP Alt Mode
   converted to HDMI by a dock (the relevant GPU signalling differs).
2. At 1080p60 inspect colour using the monitor OSD.
3. At 4K30 inspect colour again, and confirm a stable internal eDP.
4. Only if actually offered, test 4K60 with the monitor OSD and record
   whether RGB, bit depth, timing and HDR are correct.
5. Compare RGB_ONLY versus RGB8_STRICT, record hotplug and black-screen
   behaviour; do not add another new Kext patch during this comparison.

If colour gets worse, restore your backed-up existing override file.
If none existed, remove *only* the new E1.2-created product plist, never
the whole vendor directory. Reboot. Use the intact recovery EFI if the
new display override results in an unusable display. Do not unplug a live
external macOS boot disk.

## Step 4: only if EDID overrides fail

A future kernel modification would require a real Display13 read-only
register capture of the HDMI/DP pipe and monitor colour negotiation.
Only then should an optional port-scoped RGB/BPC patch be considered.
No global CSC, gamma, palette, pipe or GPU-clock changes are authorized
by this experimental branch.

## Static validation

~~~sh
python3 -m py_compile e12/tools/edid_rgb8.py
python3 -m unittest discover -s e12/tests -v
~~~

These tests use synthetic EDIDs. Passing them does not demonstrate an
installed macOS override, a correct physical colour output, or stable 4K60.
